## 0. What this document is

Narrowed implementation spec for v0.3.2. v0.3.1 shipped the internal loopback MCP path
(`127.0.0.1:8899/mcp`) for the CC subprocess only. v0.3.2 extends MCP to external clients
(Cursor, Goose) over HTTPS on the main port, and fixes the v0.3.1 deferred stale-tool-list
problem.

This spec covers two parallel slices:

- **Slice A — Dynamic tool list.** `*mcp.Server` learns about tools added/removed by
  supervisor reconnects without requiring CC to reconnect.
- **Slice B — HTTPS `/mcp` + manual API tokens.** External MCP clients connect to
  `https://<host>:8898/mcp` with a Bearer token the user manually created via REST API.
  The interactive PKCE flow and OAuth discovery metadata are both deferred to v0.3.3
  (publishing a `/.well-known/oauth-authorization-server` that advertises 501 endpoints
  would mislead clients into a discovery flow that immediately fails — see deep-review
  finding HIGH-1, 2026-05-11).

**Deferred to v0.3.3:**
- `/oauth/authorize` + `/oauth/token` (full PKCE authorization-code flow)
- `/.well-known/oauth-authorization-server` discovery metadata
- Dynamic client registration (RFC 7591)
- Refresh tokens
- Token TTL / expiry policy
- Token management web UI
- Scope model (v0.3.2 tokens are all-or-nothing)

**Deferred to v0.4:**
- `workspace_run_shell` (PTY wrapping)
- Per-task MCP lifecycle (polyforge task start/pause spawning/killing MCP servers)
- EventStore stream resumption

## 3. Slice A — Dynamic tool list refresh

### 3.1 Approach

Registry-observer callback. Chosen over (a) supervisor-direct-`*mcp.Server` reference
(too tightly coupled — supervisor must not know about the MCP server) and (b) periodic
diff polling (extra goroutine, latency, no signal of "what changed").

### 3.2 Interface changes

**`internal/mcp/registry/registry.go`** — additive only.

```go
// RegistryEvent describes a tool-set change for a single server.
type RegistryEvent struct {
    Server  string       // server name (e.g. "fs")
    Added   []ToolEntry  // tools newly registered (or replaced) since last event
    Removed []ToolEntry  // tools dropped (with their old PrefixedName)
}

type Observer func(RegistryEvent)

func (r *Registry) AddObserver(fn Observer)
```

**Semantics:**

- `Register(cfg, tools)` for a server:
  - If server was already registered: compute Removed = (old set − new set),
    Added = (new set − old set) by tool Name + Schema equality.
  - If server is new: Added = all tools, Removed = nil.
- `Deregister(serverName)`: Removed = all tools the server had; Added = nil.
- Observers are invoked in `AddObserver` order, **after** the registry's write lock is
  released, to avoid deadlocks if an observer reads back from the registry.
- Observer panics are recovered and logged via `slog.Error`; one bad observer must not
  break others.
- **Non-blocking contract** (deep-review MED-4, 2026-05-11): observers run synchronously
  in the goroutine that called `Register`/`Deregister` (the supervisor goroutine).
  Observer bodies MUST be non-blocking — return within tens of milliseconds. The
  BuildMCPServer observer (§3.3) qualifies: `srv.AddTool` / `srv.RemoveTools` are O(1)
  per tool, no I/O. Future observers that need to do longer work MUST hand the
  RegistryEvent off to their own goroutine and return immediately. Documented as a
  contract on `AddObserver`; not enforced at runtime (a slow observer would only delay
  reconnect, not break correctness).

## 4. Slice B — HTTPS `/mcp` + manual API tokens

### 4.1 New package `internal/auth/apitoken`

```go
package apitoken

type Token struct {
    ID        string    `json:"id"`         // ULID-ish (crockford32, 26 chars)
    Name      string    `json:"name"`       // user label, e.g. "cursor-laptop"
    Hash      string    `json:"hash"`       // hex(sha256(raw))
    CreatedAt time.Time `json:"created_at"`
}

type Store struct {
    path string
    mu   sync.RWMutex
    toks []Token
}

func Open(path string) (*Store, error)
func (s *Store) Create(name string) (rawToken string, t Token, err error)
func (s *Store) List() []Token
func (s *Store) Revoke(id string) error
func (s *Store) Validate(rawToken string) bool
```

**Storage format** (`~/.tether/api-tokens.json`, mode 0600):
```json
{"tokens":[{"id":"01J...","name":"cursor-laptop","hash":"<sha256-hex>","created_at":"2026-05-11T..."}]}
```

**Implementation notes:**

- Raw token = 32 random bytes hex-encoded (64 chars). Created via `crypto/rand`.
- `Hash = hex(sha256(raw))`. Constant-time compare on validate via `crypto/subtle`.
- `Create` returns the raw token **once**; the store keeps only the hash.
- `Validate` is O(N) over tokens; acceptable — N is bounded by `MaxTokens = 100` (deep-review LOW-9, 2026-05-11). `Create` returns `ErrTooManyTokens` once the cap is reached; operator must `Revoke` before adding more.
- `Name` is **required and non-empty** (deep-review HIGH-2, 2026-05-11): forces the operator to label each long-lived credential. Trimmed; max 64 chars. Duplicates allowed.
- **File permissions** (deep-review HIGH-3, 2026-05-11):
  - Parent directory `~/.tether/` must be mode 0700; `Open` verifies and chmod's if wider.
  - Final file: 0600 via `os.OpenFile(path, O_WRONLY|O_CREATE|O_TRUNC, 0600)` on first write.
  - Temp file: created in the same directory as the final file via `os.CreateTemp(dir, "api-tokens-*.json")`, then immediately `chmod 0600` before any write, then rename.
  - Tests assert mode on parent dir, final file, and temp file (via injected fs stub).
- `Open` creates an empty store if file is absent (and creates the parent dir with 0700 if missing).

**Security tradeoff — manual tokens, no expiry** (deep-review HIGH-2, 2026-05-11):

v0.3.2 manual tokens are long-lived, all-scope, internet-facing credentials. This is a deliberate scope choice (operator confirmed during brainstorming): the alternative — making external MCP unreachable until v0.3.3 — is worse for dogfooding. Mitigations:

1. Each token must be named — encourages "one token per client" hygiene and surfaces in `List` for audit.
2. Audit logging (§4.7) records create / revoke / auth-failure events.
3. Operator guidance (§9) documents revoke-and-recreate as the rotation primitive.
4. Token cap (`MaxTokens = 100`) bounds blast radius.

TTL, scope, and dynamic registration land in v0.3.3 (see §8).

### 4.2 REST API in `mux.go`

Three routes, all behind the existing JWT cookie gate (same gate that protects
`/api/v1/sessions/*`). Cross-origin CSRF posture is the existing
`withOriginGuard` (rejects POST/DELETE whose `Origin` header is present but
not allow-listed).

**Endpoint contract** (deep-review-2 MED-9, 2026-05-11 — explicit response shapes):

| Method | Path | Auth | Request body | Success | Error |
|---|---|---|---|---|---|
| `POST` | `/api/v1/mcp/tokens` | JWT cookie | `{"name":"<1..64 chars, required>"}` | `200`<br>`{"id":"<26-hex>","name":"...","token":"<64-hex>","created_at":"<RFC3339>"}` | `400` body parse / empty name / name too long / store full |
| `GET` | `/api/v1/mcp/tokens` | JWT cookie | — | `200`<br>`{"tokens":[{"id":"<26-hex>","name":"...","created_at":"<RFC3339>"}, ...]}` | — |
| `DELETE` | `/api/v1/mcp/tokens/{id}` | JWT cookie | — | `204` No Content | `404` if id absent |

**Token response field (`token`) is the raw 64-char hex Bearer value.** It is
returned **exactly once** at creation time; subsequent `GET` responses omit
it. The store keeps only `SHA-256(token)` — there is no recovery path. Operator
must `DELETE` and re-create on loss.

**Validation:** `POST` body parses as JSON; `name` trimmed of whitespace; if
empty, returns `400 "apitoken: name required"`. If `> 64` chars, returns
`400 "apitoken: name exceeds 64 chars"`. If the store is at `MaxTokens=100`,
returns `400 "apitoken: store full (max 100)"`.

### 4.3 OAuth discovery — deferred to v0.3.3

Originally planned for v0.3.2 as a forward-compat stub. Removed per deep-review HIGH-1
(2026-05-11): publishing `/.well-known/oauth-authorization-server` that advertises 501
`/oauth/authorize` and `/oauth/token` endpoints would mislead any spec-compliant client
into a failed discovery flow. The well-known document only becomes useful when the
endpoints it points to actually work — which is exactly v0.3.3's scope.

v0.3.2 ships **no** OAuth discovery endpoint and **no** OAuth route stubs. External
clients are configured with a manual token out-of-band (operator copies the token from
the `POST /api/v1/mcp/tokens` response).

### 4.4 HTTPS `/mcp` handler

`mux.go:registerMCPStubs` is removed. In its place, when `apitoken.Store` is wired into
`newServer`, register:

```go
mux.Handle("/mcp", mcpHTTPSHandler(mcpSrv, store))
mux.Handle("/mcp/", mcpHTTPSHandler(mcpSrv, store))
```

with:

```go
func mcpHTTPSHandler(mcpSrv *mcp.Server, store *apitoken.Store) http.Handler {
    sdkHandler := mcp.NewStreamableHTTPHandler(
        func(_ *http.Request) *mcp.Server { return mcpSrv },
        &mcp.StreamableHTTPOptions{SessionTimeout: 30 * time.Minute},
    )
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        auth := r.Header.Get("Authorization")
        if !strings.HasPrefix(auth, "Bearer ") {
            http.Error(w, "unauthorized", http.StatusUnauthorized); return
        }
        raw := strings.TrimPrefix(auth, "Bearer ")
        if !store.Validate(raw) {
            http.Error(w, "unauthorized", http.StatusUnauthorized); return
        }
        sdkHandler.ServeHTTP(w, r)
    })
}
```

`mcpSrv` is the same singleton passed into `MCPLoopback`. Slice A's observer keeps both
ingresses consistent.

### 4.7 Audit logging (deep-review MED-5, 2026-05-11)

Structured slog events emitted on every token-lifecycle and auth-failure event.
**Never** include the raw token or the SHA-256 hash in any log field.

| Event | When | Fields |
|---|---|---|
| `mcp.apitoken.created` | After successful `Create` | `id`, `name` |
| `mcp.apitoken.revoked` | After successful `Revoke` | `id` |
| `mcp.apitoken.auth_failed` | `/mcp` returns 401 | `remote_addr` (sanitised, no port), `reason` (`"missing_header"` / `"bad_scheme"` / `"unknown_token"`) |
| `mcp.apitoken.auth_ok` | `/mcp` succeeds auth | `id`, `name`, `remote_addr` |

Tests assert each event fires with the expected fields and that no field equals the raw token or hash.

## 7. Risks & mitigations

| Risk | Mitigation |
|---|---|
| Observer runs in supervisor goroutine; long-running `AddTool` blocks reconnect | `AddTool`/`RemoveTools` are O(1) per tool; net work ≤ ms |
| go-sdk `RemoveTools` not available or differently named | Verify API at implementation start; spec assumes it; fallback would be `srv.SetTools(snapshot)` if SDK has such a setter |
| Token store JSON corrupted by external editor | `Open` fails fast with clear error; daemon refuses to start until file fixed or removed |
| External clients leak Bearer token in logs | Documented in token-create response: "treat as a password"; UI / CLI surfaces will warn explicitly when v0.3.3 lands |
| Same MCP server reachable via two paths with different auth strengths (loopback = bearer; HTTPS = manual token) | By design — loopback token is daemon-internal and never leaves the host; manual token is the external-network credential |
| Shared singleton couples loopback + external client tool lifecycle (deep-review LOW-8) | Acknowledged. Per-task MCP isolation is on v0.4 roadmap; revisiting the singleton at that time is in-scope for the v0.4 spec |

## 9. Operator guidance (deep-review MED-6, 2026-05-11)

**Creating a token for an external client (Cursor, Goose, etc.):**

```bash
# Operator runs from their machine; JWT obtained via existing tether auth flow.
curl -H "Authorization: Bearer $TETHER_JWT" \
     -H "Content-Type: application/json" \
     -d '{"name":"cursor-laptop"}' \
     https://<tether-host>:8898/api/v1/mcp/tokens
# Response: {"id":"01J...","name":"cursor-laptop","token":"<64-hex>","created_at":"..."}
# Copy the `token` field into the client's MCP configuration. Token is shown ONCE.
```

**Rotating a token (suspected leak, employee offboard, periodic refresh):**

```bash
# 1. Create a new token with the same name + "-v2" suffix (or a distinct name)
curl ... -d '{"name":"cursor-laptop-v2"}' https://.../api/v1/mcp/tokens
# 2. Update the client configuration to the new token; verify it works.
# 3. Revoke the old token by id.
curl -X DELETE -H "Authorization: Bearer $TETHER_JWT" \
     https://<tether-host>:8898/api/v1/mcp/tokens/01J...
```

**Lost token (token text no longer recoverable):**

Tokens are stored hashed; the raw value cannot be recovered. The remedy is to `DELETE`
the entry by `id` (from `GET /api/v1/mcp/tokens`) and create a fresh one.

**Suspected leak (token may have ended up in logs / chat / screenshot):**

Revoke immediately with `DELETE /api/v1/mcp/tokens/{id}`. Inspect daemon logs for
`mcp.apitoken.auth_ok` events with that token's `id` — they record `remote_addr` and
timestamps for forensic review.

**Audit log location:**

slog default sink. Operators redirect daemon stderr to their preferred log aggregator;
all token events use the `mcp.apitoken.*` prefix for filtering.

**Browser-based MCP clients are out of scope for v0.3.2.** The `/mcp` endpoint is
registered behind the daemon's existing `withOriginGuard` (the CSRF posture for
all `/api/v1/*` endpoints). External native clients (Cursor, Goose) send no
`Origin` header on their JSON-RPC POSTs and pass through unchanged. A
browser-hosted MCP client would be 403'd. This is intentional — browser-side
support arrives naturally with v0.3.3's OAuth 2.1 `/authorize` redirect, which
establishes a same-origin session before any `/mcp` POST happens.

**Time field format:** API responses encode `created_at` as Go's default
`time.Time` JSON marshaller, which emits RFC3339Nano (`"2026-05-11T13:45:22.123456789Z"`).
Downstream consumers MUST accept the nanosecond suffix or use an RFC3339-flexible
parser. (Verifier-3 low: spec text previously claimed RFC3339 plain.)
