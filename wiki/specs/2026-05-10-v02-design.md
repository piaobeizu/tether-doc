# tether v0.2 design spec

**Date:** 2026-05-10
**Author:** wxk + Claude
**Status:** Draft — pending implementation plan

## Goal

Ship three independent features as tether v0.2:
1. **Auth** — static token gate; prevent public-internet access by random users
2. **opencode provider** — second AgentProvider (A2 per-prompt spawn); per-session selector in UI
3. **multi-tab attach** — second browser tab can attach to an existing session via EventBus fan-out

Each feature is independently deployable. No shared prerequisite.

## Out of scope (v0.2)

- Multi-token / per-device revocation (v1.0)
- Full login page with username/password (v1.0)
- CLI `tether attach <sid>` raw-mode TTY (v1.0+)
- Gemini / Cursor / Codex providers (v1.0+)
- Historical event replay on attach (v1.0+)
- Cross-device attach from different host/network (v1.0+)

## §1 Auth — static token gate

### Threat model

Single-user, single-machine daemon exposed on a public IP. Goal: prevent unauthenticated access by anyone who knows the host:port. Not defending against a compromised server or multi-user isolation (v1.0).

### Token lifecycle

1. On startup, if `~/.tether/access-token` does not exist: generate 32-byte random hex token, write to file (mode 0600), print to stdout:
   ```
   tether access token: <token>
   ```
2. `--token <secret>` flag overrides the auto-generated token (useful for automation / scripted deploys).
3. JWT signing secret is generated separately at `~/.tether/jwt-secret` (mode 0600). Survives daemon restarts — existing cookies stay valid after restart.

### Request flow

```
First visit (no cookie)
  → redirect to /auth

POST /api/v1/auth/verify { "token": "<value>" }
  → daemon compares against stored token (constant-time)
  → on match: issue JWT, set HttpOnly cookie `tether_session` (no expiry)
  → on mismatch: 401

Subsequent requests
  → auth middleware reads cookie → validates JWT → passes to handler
  → 401 on invalid/missing cookie → frontend redirects to /auth
```

### Backend

New package `internal/auth/`:
- `token.go` — read/write `~/.tether/access-token`, `--token` override
- `jwt.go` — sign/verify JWT (HS256, secret from `~/.tether/jwt-secret`)
- `middleware.go` — HTTP middleware: check cookie, pass or 401

Routes exempt from auth middleware: `GET /auth`, `POST /api/v1/auth/verify`, static assets (`/`, `/*.js`, `/*.css`, `/favicon.*`).

All `/api/v1/*` and `/wt/*` routes wrapped with auth middleware.

### Frontend

- `/auth` route: single-field form (access token input + submit button). No design ceremony — functional only.
- On 401 from any API or WT upgrade: redirect to `/auth?redirect=<original-path>`.
- After successful verify: redirect back to original path.

### Wire changes

New endpoints (no tygo codegen needed — auth is REST only):
```
POST /api/v1/auth/verify    body: { token: string }
                            response: 200 | 401
DELETE /api/v1/auth/session logout (clears cookie) — v1.0, stub 501 for now
```

## §2 opencode provider

### Integration class

A2 (per-prompt spawn) per D-17a §2. Already validated in PoC step9.

```
[per user message]
  spawn: opencode run --format json -s <sid> "<prompt>"
  parse stdout (newline-delimited JSON) until process exit:
    { "type": "text",         "content": "..." }  → EventKindAssistantText
    { "type": "step_finish",  ... }               → EventKindResult
    { "type": "step_start",   ... }               → ignored
```

Session persistence: opencode stores session state on disk keyed by `<sid>`. Between prompts, the subprocess exits; the next prompt restores context from disk. Daemon is stateless per-prompt.

### Backend

`internal/agent/opencode_provider.go` — implement `AgentProvider`:
- `Name() string` → `"opencode"`
- `Spawn()` → records sid, returns an `opencodeSession`
- `opencodeSession.SendPrompt()` → `exec.CommandContext("opencode", "run", "--format", "json", "-s", sid, prompt)`, stream stdout
- `opencodeSession.Events()` → channel fed by stdout parser goroutine
- `opencodeSession.Interrupt()` → kill active subprocess if running
- `opencodeSession.Close()` → no-op (subprocess already exited)

Estimated ~80 LOC (matches D-17a estimate).

`internal/session/registry.go`:
- `NewSession(ctx, providerName string) (*Session, error)`
- Registry holds a `map[string]agent.AgentProvider` keyed by name
- Default: `"claude"`; unknown name → error

### Wire / tygo

`internal/wire/session.go` — add field:
```go
type NewSessionRequest struct {
    Provider string `json:"provider,omitempty"` // "claude" | "opencode"; default "claude"
}
```
Run `make tygo` → auto-generates `web/src/lib/wire.gen.ts` update.

### Frontend

Provider selector in the new-session UI (same visual position as cloudcli model selector):
- Dropdown: `[ claude ▼ ]` / `[ opencode ▼ ]`
- Selected provider stored in component state, sent in `NewSessionRequest.provider`
- Active session header shows provider name as a chip/badge
- Available providers fetched from `GET /api/v1/providers` → `{ providers: string[] }`

New endpoint: `GET /api/v1/providers` → returns list of registered provider names. Allows frontend to populate the dropdown without hardcoding.

## §3 multi-tab attach

### Current state

`/wt/events` has one WT consumer per session. The provider writes events to a single `chan Event`; one goroutine reads and forwards to the single connected WT stream.

### EventBus fan-out

New type `session.EventBus`:

```go
type EventBus struct {
    mu   sync.RWMutex
    subs map[string]chan agent.Event  // key = subscriber ID (UUID)
}

func (b *EventBus) Subscribe() (id string, ch <-chan agent.Event)
func (b *EventBus) Unsubscribe(id string)
func (b *EventBus) Publish(e agent.Event)  // non-blocking: full channel → drop + log
```

`Publish` holds a read lock while iterating subscribers. Slow consumer whose channel is full gets the event dropped (logged at WARN level) rather than blocking other subscribers or the provider goroutine.

Buffer size per subscriber channel: 64 events (configurable via const).

### Session integration

`internal/session/session.go`:
- Replace `events chan agent.Event` field with `bus *EventBus`
- Provider writes via `bus.Publish(e)`
- `/wt/events` handler subscribes/unsubscribes per connection

### /wt/events handler

```
1. Parse ?sid= from URL query
2. Look up session in registry (must exist and be active)
3. id, ch := session.Bus.Subscribe()
4. defer session.Bus.Unsubscribe(id)
5. For e := range ch { write to WT stream }
```

Second browser tab: opens `/wt/events?sid=<existing-sid>` → immediately starts receiving new events. No replay of past events (attach sees only future output).

### Frontend

Session list view gains an **Attach** button next to each active session. Clicking it:
1. Opens `/wt/events?sid=<sid>` WT connection
2. Renders chat output in read-only mode (second tab cannot send prompts — only the "owner" tab can write)
3. Session header shows `[read-only / attached]` indicator

Write restriction in v0.2: only one tab sends prompts (enforced client-side; server-side lock enforcement is v1.0).

## Acceptance criteria

- [ ] `tether server` with no `--token` flag: prints token to stdout on first run, stores in `~/.tether/access-token`
- [ ] Browser visit without cookie: redirected to `/auth`; after correct token: cookie set, redirected back
- [ ] Wrong token: 401, stays on `/auth`
- [ ] Provider dropdown visible on new session; opencode session produces assistant text events
- [ ] Two browser tabs attached to same session: both see new events in real time
- [ ] Second tab is read-only (cannot send prompts)
- [ ] `tether doctor` updated to check opencode binary presence (if provider configured)
