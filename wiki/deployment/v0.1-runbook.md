## 0. Preflight

### System requirements

| Tool          | Min version | Why |
|---            |---          |---  |
| Go            | 1.25.0      | matches `tether/go.mod`; older toolchains fail at build time |
| Rust          | 1.90 stable | matches the version Tauri 2 + the `web-transport-quinn` deps need |
| Node.js       | 20.x        | for Vite + `@tauri-apps/cli` |
| pnpm or npm   | recent       | tether-app's `package.json` works with either |
| `claude`      | latest      | Anthropic Claude Code CLI; `which claude` must succeed |
| RAM           | 8 GB+ rec.  | Tauri 2 `tauri:dev` builds + cargo + a real cc session |
| Disk          | ~5 GB free  | Cargo target/, node_modules, JuiceFS NOT in scope here |

Optional, only if you want the Android target on this box:
Android NDK r26+ — see [`./android-build-pipeline.md`](./android-build-pipeline.md).

### Required env

```bash
# cc itself talks to the Anthropic API; if this is unset cc will refuse
# to run any tool calls and the auth-broker loop has nothing to gate.
export ANTHROPIC_API_KEY=sk-ant-...
```

### Network

- The daemon's WebTransport listener binds to whatever address you pass
  to `--wt-addr` (e.g. `:4444`). WT runs over QUIC/UDP. On a single
  machine, `localhost:4444` is enough — no firewall changes.
- Cross-machine pair (phone ↔ laptop) requires UDP/`<wt-port>`
  reachability between the two devices. Out of scope for v0.1 same-host
  dogfood; pair across networks lands as a follow-up.

### Disk paths the daemon owns

The daemon reads / writes only under these roots — no system files
touched.

```
~/.tether/                                         (created on first run, 0700)
├── attach.sock                                    UDS for the local TUI attach client (0600)
├── cc-settings/settings.json                      cc hookserver config (0600); only when --auth-broker
└── users/default/
    ├── audit.log                                  pair handshake audit, append-only
    ├── devices/                                   pair registry (one .json per paired device, 0700)
    └── sessions/default/lock.log                  lock state-machine audit log, 0600
~/.claude/projects/<encoded-cwd>/<sid>.jsonl       cc-owned; daemon tails it read-only
```

## 1. Clone + build

Three repos. Workspace layout is your choice; below assumes a peer
layout under `~/code/tether/`:

```bash
mkdir -p ~/code/tether && cd ~/code/tether
git clone git@github.com:piaobeizu/tether.git
git clone git@github.com:piaobeizu/tether-app.git
git clone git@github.com:piaobeizu/tether-doc.git
```

### Daemon (Go)

```bash
cd ~/code/tether/tether
go install ./cmd/tether
# Binary lands at $(go env GOPATH)/bin/tether — make sure that's on PATH.
tether help
```

Expected `tether help` output starts with:

```
usage: tether <subcommand> [flags]

Subcommands:
  daemon                         start the supervised daemon ...
  skill install <name|git-url>   ...
  skill list [--json]            ...
  skill remove <name>            ...
  skill info <name>              ...
  resume <sid>                   resume a claude session by id ...
  tether-blob-register <path>    (v0.1 stub) ...
  help                           show this message
```

If `tether: command not found`, your `$GOPATH/bin` is not on `PATH`.
Add `export PATH="$(go env GOPATH)/bin:$PATH"` to your shell rc.

### Desktop app (Tauri 2)

```bash
cd ~/code/tether/tether-app
pnpm install            # or `npm install`
pnpm tauri:dev          # dev build with hot-reload; opens a Tauri window
# OR for a release bundle (.dmg / .deb / .AppImage / .msi):
# pnpm tauri:build
```

`tauri:dev` will stream cargo build output the first time. Expect a
~3-5 minute first build (full cargo compile of `quinn`, `ring`,
`web-transport-quinn`, etc.). Subsequent runs are incremental.

If you hit a **stronghold KDF `compile_error!`** during the first
cargo compile, you're on a pre-B2 commit; pull `tether-app` main and
rerun. (See landmine #6 below.)

### Doc repo

```bash
cd ~/code/tether
git clone git@github.com:piaobeizu/tether-doc.git
# Markdown only — nothing to build.
```

## 2. First-run daemon start

Single command, in a dedicated terminal. Leave this running for the
rest of the runbook.

```bash
tether daemon -v --auth-broker --wt-addr :4444
```

What each flag does (verified against `cmd/tether/main.go`):

| Flag                | What it does |
|---                  |---           |
| `-v`                | verbose supervisor logging; surfaces hookserver addr, audit-log paths, **and the WT cert SHA256 you'll need in step 3** |
| `--auth-broker`     | enables the tool-authorization broker + cc hookserver. Without this, PreToolUse hooks fail-closed and the auth modal in the app never fires |
| `--wt-addr :4444`   | binds the WebTransport listener to `:4444`. Empty / omitted disables WT entirely (desktop app cannot connect). |

### What gets created on disk

First-run side effects (all 0700 / 0600 — daemon-owned):

```
~/.tether/                                            (mkdir 0700)
~/.tether/cc-settings/settings.json                   (mkdir + write, 0700 / 0600)
~/.tether/users/default/audit.log                     (touch, 0600)
~/.tether/users/default/devices/                      (mkdir 0700)
~/.tether/users/default/sessions/default/lock.log     (touch 0600)
~/.tether/attach.sock                                 (UDS bind, 0600 — recreated on every run)
~/.claude/projects/                                   (mkdir 0700 if missing — cc writes here)
```

### Daemon log lines that matter (with `-v`)

A clean startup, in order, looks like (fields elided):

```
[daemon] lock audit log → /home/you/.tether/users/default/sessions/default/lock.log
[daemon] hook server listening at http://127.0.0.1:NNNNN; cc settings → /home/you/.tether/cc-settings/settings.json
tether daemon: cc settings → /home/you/.tether/cc-settings/settings.json
[daemon] pair audit log → /home/you/.tether/users/default/audit.log
[daemon] pair registry → /home/you/.tether/users/default/devices
[daemon] wt listener starting on :4444
wt: dev cert auto-generated (DER sha256=8a3f7e...)
```

> **CRITICAL** — copy the hex value after `DER sha256=` from the
> `wt: dev cert auto-generated` line. This is the **pinned cert
> SHA256** the desktop app needs in step 3. The dev cert is
> regenerated on **every daemon restart**, so this hex changes each
> time you `Ctrl+C` and restart the daemon.

### Stopping the daemon

`Ctrl+C` in the daemon terminal. The watchdog drains supervised
goroutines and the process exits 0. You'll see:

```
tether daemon: signal interrupt received, shutting down
```

`~/.tether/attach.sock` is removed; everything else (audit logs,
device registry) persists across restarts.

## 3. Configure desktop app

With the daemon running and you having copied the DER SHA256 from
step 2, switch to the Tauri window (the one `pnpm tauri:dev` opened).

1. Navigate **Settings → Connection**.
2. Fill in:
   - **Daemon URL**: `https://localhost:4444`
     (HTTPS — WebTransport's HTTP/3 layer terminates TLS at the
     daemon's listener; the dev cert is what makes the SHA256 pin
     necessary.)
   - **Pinned cert SHA256**: paste the hex you copied from the
     `DER sha256=` log line. No `0x` prefix, no spaces.
   - **Session ID**: leave blank for the first connect, or pick an
     existing cc session id from
     `ls ~/.claude/projects/<encoded-cwd>/`. Each `.jsonl` filename
     (minus the extension) is a valid session id.
3. Save.
4. The state badge in the app's header should now read **`needs-pair`**.
   That's expected — no devices have been paired yet.

If the badge instead reads `disconnected` and you see "TLS handshake
failed" in the app's log panel, recheck the DER SHA256 (most common
cause of this).

## 4. First pair flow

Same machine, same user, two windows: the daemon terminal (step 2) and
the Tauri app (step 3). The pair handshake here trusts yourself —
real cross-device pair is the same flow with two humans visually
comparing the SAS.

1. In the app, **Settings → Connection → "Pair new device"**.
2. The Tauri Rust side calls the `pair_start` command, opens a fresh
   WT control stream to the daemon, and sends a `pair.invite` envelope
   (spec §11.AB).
3. The daemon's WT subsystem peeks the first JSON line, sees
   `kind=pair.invite`, and runs the responder side of the FSM.
4. Both sides derive the **6-character SAS** (e.g. `J8LNUS`) from the
   X25519 shared secret + a transcript hash. The SAS shows on both UIs.
5. **Same-machine**: visual compare is trivial — click **"It matches"**
   on the initiator. The responder side auto-confirms (the daemon
   doesn't have a separate UI; it accepts when the initiator's
   `pair.sas-confirm{ok:true}` arrives).
   **Two-device**: human compares the 6 chars on both screens, clicks
   "It matches" on each.
6. On success:
   - The daemon writes `~/.tether/users/default/devices/<deviceId>.json`
     containing the long-term shared key.
   - The daemon appends `pair.success` to
     `~/.tether/users/default/audit.log`.
   - The app's "Paired devices" list shows a new row with the
     deviceId + display name.
   - The state badge auto-flips: `needs-pair` → `connecting` →
     `connected`.

If pair fails — SAS mismatch (genuine attack, or a bit-flip on the
wire), timeout, or the responder cancelled — the daemon emits
`pair.fail` to the audit log with a reason field, and the app surfaces
the abort code (`sas-mismatch`, `timeout`, `protocol-violation`,
`cert-error`, etc.).

## 5. Real cc dogfood

Now everything is wired: daemon up, app paired, control channel
authenticated. Time to drive a real `claude` session through the
hook-server gate.

1. Open a **new terminal** (separate from the daemon and the Tauri
   app).
2. Pick a session id. For the very first run, just generate one:

   ```bash
   SID=$(uuidgen)
   ```

   Or grab an existing one from
   `ls ~/.claude/projects/<bucket>/`.
3. Resume / start the cc session through tether's wrapper:

   ```bash
   tether resume "$SID"
   ```

   What this does (spec §10.4 strategy c, verified in
   `cmd/tether/resume.go`):
   - Decodes the bucket from `~/.claude/projects/` to find the cwd cc
     was last in for that session id.
   - Resolves the cc settings.json path via the precedence chain:
     `--settings` flag → `TETHER_HOOK_SETTINGS` env →
     `$HOME/.tether/cc-settings/settings.json` (which step 2 created).
   - `execve`s `claude --resume <sid> --settings <path>` so cc reads
     hooks from that settings file.

   For a brand-new session that doesn't yet exist on disk, run cc
   directly with the settings flag the daemon wrote:

   ```bash
   claude --settings "$HOME/.tether/cc-settings/settings.json"
   ```

   (Once cc has spilled at least one JSONL to
   `~/.claude/projects/<bucket>/<sid>.jsonl`, `tether resume <sid>`
   takes over.)

4. Inside cc, prompt something that fires a `Bash` tool call:

   ```
   run `ls /tmp` via Bash
   ```

5. End-to-end flow you should observe:
   - cc emits `PreToolUse` hook → POSTs to
     `http://127.0.0.1:NNNNN/hooks/PreToolUse` (the hookserver from
     step 2).
   - Daemon's `agent.AuthBroker` constructs `auth.tool-request`
     envelope → emitter dispatches it on the WT events channel for
     the active session → app receives it.
   - **Modal pops up in the Tauri app**: "Allow tool: Bash?" with the
     command preview (`ls /tmp`).
   - Click **"Allow once"** → app sends an `auth.tool-decision` frame
     on the WT control channel → daemon's per-session control-stream
     dispatcher routes it to the broker → broker resolves the pending
     `Ask()`.
   - hookserver returns `{decision: "allow"}` → cc executes
     `ls /tmp` → output renders in the cc terminal.
   - The cc transcript JSONL appears in
     `~/.claude/projects/<bucket>/<sid>.jsonl`; the daemon's
     emitter tails it and dispatches each new line as an envelope to
     the app, which renders the conversation in its chat surface.

Both halves of the loop are visible:
- cc actually runs the tool (terminal output).
- The app shows what cc said + the auth gate fired (modal + chat
  surface).

That's v0.1 dogfood. From here you can iterate: deny a tool call and
watch cc handle it, kill the daemon mid-call and watch the app reflect
the broken transport, etc.

## 6. Common errors + fixes

| Symptom | Check | Fix |
|---|---|---|
| **"TLS handshake failed"** in app log | does the pinned cert SHA256 in Settings → Connection match the latest `DER sha256=` line in the daemon's `-v` startup output? | dev cert is regenerated on every daemon restart; copy the new hex into the app and reconnect. |
| **"Daemon not reachable"** | `ps -ef \| grep '[t]ether daemon'` — is the daemon process alive? `ss -ulpn \| grep 4444` — is the WT port bound? | restart the daemon. Confirm `--wt-addr :PORT` matches the `:PORT` in the app's Daemon URL. |
| **`tether: command not found`** | `which tether` after `go install ./cmd/tether` | add `$(go env GOPATH)/bin` to `PATH`. |
| **`claude: command not found`** | `which claude` | install Anthropic's Claude Code CLI per their docs. |
| **Auth modal never appears / cc hangs on Bash** | did you start the daemon with `--auth-broker`? does `~/.tether/cc-settings/settings.json` exist? are you running cc via `tether resume <sid>` (or `claude --settings <path>`)? | re-start daemon with `--auth-broker`. Re-run cc via `tether resume <sid>`, OR for a brand-new session: `claude --settings $HOME/.tether/cc-settings/settings.json`. Bare `claude` (no `--settings`) bypasses the hookserver entirely. |
| **"Paired devices" list empty after a pair flow** | `ls ~/.tether/users/default/devices/` — any `.json` files? `grep pair ~/.tether/users/default/audit.log \| tail -5` — was the last line `pair.success` or `pair.fail`? | re-run pair. If audit shows `pair.fail`, the `reason` field tells you which abort kind: `sas-mismatch`, `timeout`, `cert-error`, etc. |
| **App stuck in `needs-pair` after a successful pair** | this was a real bug pre-PR #21 (the C2 fix) | pull `tether-app` main and rebuild. |
| **Re-pair rejected: `dup-deviceid`** | per spec §14 Q2, v0.1 default for re-pair of an existing deviceId is **reject** | in the app, Settings → Connection → "Forget device" first, then re-run pair. The forget side deletes both `~/.tether/users/default/devices/<deviceId>.json` on the daemon AND the local long-term key in stronghold on the app. |
| **`stronghold` KDF `compile_error!` during cargo compile** | post-B2 (Argon2id) this is gone; if you hit it you're on a pre-B2 commit | pull `tether-app` main + rebuild. Temporary unblocker for dev-only builds: `cargo build --features insecure-kdf` (do NOT ship a release with this). |
| **JSONL not appearing under `~/.claude/projects/`** | is cc actually writing? `tail -f ~/.claude/projects/<bucket>/<sid>.jsonl` from a third terminal. Was `--projects-dir` overridden on the daemon? Bucket-name decoding sane? | the daemon recursively watches one directory level under `--projects-dir` (PR #45). If cc is writing to a deeper path, raise that as a follow-up. |
| **Pair audit log empty after pair flow** | `cat ~/.tether/users/default/audit.log` | the daemon did not pick up the pair attempt — most likely `--wt-addr` is unset (no WT subsystem → no pair handler). Restart with `--wt-addr :4444`. |

A note on the long-discontinued `--no-audit` flag combinations: if you
deliberately pass `--no-audit`, the lock-state JSONL audit is suppressed
in-memory only. The pair audit log has its own opt-out (`DisablePairAudit`
in `daemon.Config`); the CLI does NOT expose a flag for it in v0.1 — pair
audit is always on if the daemon can resolve `$HOME`.

## 7. Audit + observability

| What you want to see | Where to look |
|---|---|
| Lock takeovers (who held it, when handed off) | `~/.tether/users/default/sessions/default/lock.log` (JSONL; each line is a state transition) |
| Pair handshakes (success / fail / abort reasons) | `~/.tether/users/default/audit.log` (append-only; lines like `pair.success{deviceId=...}`, `pair.fail{reason=sas-mismatch}`) |
| Daemon-internal progress (heartbeats, frame counts, restarts) | the daemon's stderr — only visible with `-v`. Default `-v=off` shows only **always-on warnings** (audit-log open failures, hookserver serve errors, broker emitter Inject errors). |
| cc envelope flow into the app | `tail -f ~/.claude/projects/<bucket>/<sid>.jsonl` — every line emitted there is a candidate envelope the daemon dispatches to the app. |
| Auth-broker gate decisions | currently visible only in the daemon's verbose log + the app's audit-modal history. No persistent decision log in v0.1 (follow-up). |

Log levels:
- **`-v` on**: verbose. Heartbeats, frame counts, hook listener URL,
  pair registry path, audit-log paths, dev-cert SHA256, JSONL watcher
  errors. Loud — meant for dogfood / debug.
- **`-v` off** (default): only `warnf` — operationally rare events
  the user cannot diagnose without seeing them. There is **no**
  "between" log level in v0.1.

## 8. Production deploy hand-off

This runbook is **single-machine v0.1 dogfood only**. For real ops:

- **K8s + JuiceFS PV (multi-replica daemon)**: see
  [`./juicefs-pv.md`](./juicefs-pv.md) for the StatefulSet shape +
  manifest layout, and [`./c-prime-prime-verification.md`](./c-prime-prime-verification.md)
  for the runnable C'' verification recipe (cross-replica JSONL
  visibility, audit-log consistency).
- **Android target**: see [`./android-build-pipeline.md`](./android-build-pipeline.md)
  for NDK setup, target triples, and the `cargo check` smoke matrix.
- **iOS target**: deferred to v0.1.x per spec
  [`../specs/2026-04-26-tether-go-quic-design.md`](../specs/2026-04-26-tether-go-quic-design.md)
  D-13.

Multi-user / multi-tenant is **explicitly not v0.1**. Every path
this doc references (`~/.tether/users/default/`, `LockUser="default"`,
`PairUser="default"`) is hard-coded `default` per spec D-04. The
v0.1.x plan is to thread a real user identity through that bucket
once an auth surface exists.

## 9. v0.1 known limitations + v0.1.x roadmap

Things that work in this runbook but are deliberately incomplete in
v0.1, with the follow-up they're tracked under:

| Known limitation | What this means for the operator | Fix tracked as |
|---|---|---|
| **DAG envelope kind not yet emitted by the daemon** | The "DAG" block in the app's UI shows nothing real for v0.1. Conversation rendering still works (driven by `session.state` + `session.message` envelopes). | C1 follow-up |
| **No explicit `session.reloading` envelope** | Reload banner in the app uses a proxy: `session.state` with `recordType=system`. May misfire or miss in edge cases. | follow-up after C1 lands |
| **"Always" auth decisions are in-memory only** | Click "Always allow Bash" in the auth modal → daemon remembers it. Restart the daemon → it re-asks. | persistent decision-log follow-up |
| **`lock.log` has no rotation** | Audit log grows forever. Operator-managed for now (`mv lock.log lock.log.YYYYMMDD`). | spec §11.D follow-up |
| **`hookserver.Start` is single-shot** | If the hook subsystem panics, the watchdog cannot restart it cleanly (second `Start` returns `ErrServerStopped`). The supervisor will re-Run forever; in practice this never fires because the hookserver is stable. See `internal/daemon/daemon.go::hookSubsystem` doc. | hardening follow-up |
| **iOS deferred to v0.1.x** | `tether-app` builds for desktop + Android only. iOS plumbing is scaffolded but not wired. | spec D-13 |
| **Single-user `default` bucket** | Hard-coded everywhere — `~/.tether/users/default/...`. No multi-user surface. | spec D-04 follow-up |
| **Dev cert regenerated on every daemon restart** | Pinned SHA256 in the app must be re-pasted after each restart. Persistent dev cert is a v0.1.x convenience. | follow-up |
| **Cross-pod attach over JuiceFS** | The attach UDS is pod-local. Cross-replica attach over the network goes through the WT bridge, not JuiceFS. | spec Phase-11+ |
